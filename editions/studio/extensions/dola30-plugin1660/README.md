| 结构化任务/扣费候选 | 都为空 | 都为空 |
| 自动续确认 | 没有动作 | 没有动作，等待被新操作取消 |

成功样本说明空的任务/扣费候选不能作为失败判据，视频资源是另一路独立证据。10040 在该样本中对应思考块，不是视频任务代码，不能把修改响应类型当成触发工具。

两份导出没有额度 summary，也没有 option/ext/上下文的实际值，无法确认套餐/会话一致或指定某个路由开关为原因。两次请求体仅差两字符也不能定位具体字段，更不能据此认定是服务端随机。详见包内 `本次调试结论.md`。

## 1.6.32 修复与使用

- 去掉调试器仅分析前 256 个事件的限制；失败样本的 1260 个对象被旧版截断，结尾此前丢失。现在分析字节预算内全部事件，保留事件计数及前 16 + 后 16 个结构摘要。body 的 truncated 和事件展示的 eventsTruncated 分开。
- 记录 end_type、finish_reason、cmd 等有限流程值，结束事件不再被大量文字增量挤掉。
- 对真实提交的正文、输入框镜像、四项视频参数、完整能力对象、option/ext/user_context 计算 SHA-256，原稿与上下文内容不导出。会话/分段/机器人标识只保存摘要；请求 ID、时间戳及凭据不作为比较控制值。
- 白名单路由值与 option 的布尔值单独记录；最近两次提交在 submissionComparison 中比较，提示词未完整识别时显示未知。

加载本版并刷新页面后，可连续记录实际发生的两次提交，中间保留日志，随后导出；无需额外构造或重放生成请求。面板会显示与上次提示词、视频参数和选项相同/不同/未知。摘要不同只说明对应输入组不同，不能单独证明其因果关系；摘要相同也不能排除后端隐藏状态。

本版修复日志截断、补足提交差分，不宣称已解决稳定直出。网络观察器没有生成、重放、响应替换或自动重试代码。

## 上一轮 1.6.30 日志与 1.6.31 解析修复

用户导出的 1.6.30 记录中，Debugger 确实附加成功，浏览器发出了一次带签名的 `/chat/completion` POST，收到 HTTP 200 / 22,687 字节 SSE。页面传输观察器读取到 seedance_v2.5、30 秒、1080p；未捕获可识别任务、扣费字段或视频资源。自动续确认的 triggerCount 为 0，没有执行追加确认。

实际请求顶层键包含 `client_meta/messages/option/chat_ability/user_context/ext`。旧的两个识别器只查 `messages[].ext.chat_ability`，因此 `video:null` / `requestIntent.video:false` 不能证明视频参数没发出，前缀的 false 也不能据此判定为丢失。原导出没有消息与参数原文，无法从旧摘要重新解析或恢复前缀。

额度 summary 返回 code=0，但旧导出只存 hasActiveSubscription/is_trialing/usage_exhausted 等字段名，没有保存值，无法据此断言账号有没有体验套餐或是否耗尽。响应 schema 的前 96 项又被 ACK 会话元数据填满，后面的消息字段未完整展示。

本版针对已确认的诊断错误修复：

- 页面与 Debugger 共用 `video-request-schema.js`，识别顶层 chat_ability、原生草稿内能力和 JSON/数组/Unicode 转义的内容块；
- 前缀观察支持 true/false/null，未知结构显示“不能判断”，不会把解析不完整当成未发送；
- 记录正文来源、消息字段名、能力来源，均不记录请求原稿；
- 额度接口保留白名单中的真实布尔/数值/功能组标签，数组索引保留，以对应视频和其他额度组；
- SSE 保留逐事件类型、消息结构/块类型和结束标记，另列消息/工具相关字段路径，显式报告 schema 是否截断。

**修复的是诊断解析，未证实生成直出已修复。** 本版没有新增或猜造生成/付费权限字段，没有修改签名后的请求，也没有用助手台词伪造任务。

## 启用与采集

本版按要求新增 `debugger` 权限，真正连接标签页的 Chrome 调试协议。旧版只初始化面板，保留但没有使用的 Fetch 暂停/重写链路已经移除。本版调试层只开启 Network 事件和读取请求/响应正文，不暂停、不重放、不替换平台请求或回复。

1. 停用旧版，加载本 ZIP 的 `dola30` 目录，并刷新页面。诊断版本应为 1.6.34。
2. 国内豆包默认尝试附加。在面板看到 **“Debugger 已附加”**、扩展角标 **DBG** 后再手动生成一次。失败时显示具体原因及 ERR，不能只凭安装成功判断已经附加。
3. 如果还只返回文字，等待回复结束，点击 **“导出调试”**。生成的 JSON 同时包含网页诊断和 `debuggerNetwork` 网络记录，可直接用于分析。
4. 面板可停止、重新启用或清空记录。Dola 默认不附加，需要对照时在 Dola 面板手动启用，分别导出两站真实记录。

浏览器取消调试、打开 DevTools 或其他调试器占用可能使附加失败/断开。面板会显示真实状态，断开后不自动抢占重连；关闭占用后点“启用/重试”。这是 Chrome 调试会话的行为，见下方官方文档。

调试只覆盖附加后的请求，不追溯之前发送的请求。应先看到已附加，再进行待排查的那次生成。切换到非豆包/Dola 网站时停止采集并尝试分离，关闭标签页时清理会话。停止失败会明确显示“停止未确认”，不会假报已停止。

## 网络记录含义

| 字段 | 含义 |
| --- | --- |
| `debuggerNetwork.attached` | 当前已成功连接且启用 Network 观测 |
| `debuggerNetwork.phase / error` | 附加、停止、断开或失败原因 |
| `debuggerNetwork.lastSubmission` | 最近一次 `/chat/completion`，历史查询不会覆盖它 |
| `debuggerNetwork.submissionComparison` | 最近两次真实提交的各组摘要是否相同、路由值变化及会话摘要对比 |
| `debuggerNetwork.requests` | 当前标签页保留的最多 60 条 Fetch/XHR/EventSource 请求摘要 |
| `requests[].request.video` | 浏览器发出请求中观察到的真实视频参数；未识别为视频时为 null |
| `requests[].request.abilitySource / shape` | 能力来自顶层实际请求、原生草稿还是旧结构 |
| `requests[].request.messageKeys / textSources` | 消息字段名与实际检查过的正文来源，帮助定位未知结构 |
| `requests[].request.prefixMarkerPresent` | true 为看到了标记，false 为已检查的已知正文没有，null 为结构未知；不是调用成功 |
| `requests[].request.comparison` | SHA-256 分组摘要、路由值与标识摘要；无法计算时明确 error |
| `requests[].request.comparison.fieldDetails / replyFormat` | 逐字段摘要及覆盖标记、原生回复模板文字标记 |
| `debuggerNetwork.submissionComparison.fieldDiff` | 最近两次提交变化的具体字段；区分标识与控制/上下文 |
| `requests[].status / phase` | 原始 HTTP 状态、接收/结束/传输失败/正文不可读取等阶段 |
| `requests[].response.statusFields` | 原样结构化状态码候选 |
| `requests[].response.businessErrors` | 非零状态码与脱敏后的短错误消息候选，仍须结合协议解释 |
| `requests[].response.taskFields / billingFields` | 结构化任务和点数/额度候选；不从助手台词推断 |
| `requests[].response.schema` | 有限响应字段路径，帮助定位尚未识别的协议结构 |
| `requests[].response.schemaTruncated / detailSchema` | 基础路径是否已达上限，以及单独保留的消息/工具相关路径 |
| `requests[].response.events / eventCounts` | 事件开头/结尾的结构和所有事件名称计数，不含消息原文 |
| `requests[].response.entitlementFields` | 仅额度 summary 响应中的实际套餐/试用/耗尽/使用比例等白名单值 |

每个标签页的请求用序号区分。`kind=submission` 为提交，`history` 为历史查询，`video_related` 仅是路径分类，不等同于创建任务。历史里出现旧视频 ID 不会被当成这次生成成功。

调试器在 `Network.loadingFinished` 后读取 JSON/SSE 正文。流尚未结束时只记录状态及字节数，正文暂不可用；读取被浏览器缓存淘汰的正文会显示 `response_unavailable`。二进制和超过 2,000,000 字符/已知字节上限的正文跳过，不伪造空成功。

不保存请求原稿、Cookie/Authorization 头、查询参数、签名值或原始任务 ID；仅保留参数、结构和必要摘要。短业务错误消息会做 URL/凭据脱敏。新增 `storage` 权限用于扩展自身的会话记录；后台 worker 重启后尝试恢复并重新核验连接。扩展重新加载/更新、浏览器重启会清除这类会话存储，应先导出需要保留的记录。

**本版完成的是 Debugger 启用和真实链路采集，还没有证明国内豆包可以直接出片。** 全部结果仍标为 `UNVERIFIED`，HTTP 200、前缀或一句“正在生成”不算视频任务证明。前版生成指令与一次续确认功能继续保留，可独立关闭用于对照。

## 前版生成指令功能

1.6.28 只有回复后的“一次自动续确认”，没有给首条国内视频消息加入生成指令。1.6.29 新增默认开启的“国内生成指令前缀”，可以独立关闭。原生视频消息在签名前会补充明确要求调用视频工具的指令，保留其后原稿及素材引用。

前缀全文：

> 【视频生成请求】
> 请现在调用视频生成工具，依据以下内容和本条参考素材制作视频。模型、时长、比例、分辨率以本次视频工具参数为准，已确认，无需再次询问或改写为参数确认、分镜方案。若无法实际调用，请直接说明权限、额度或工具错误；不得用文字声称已经生成。
> 【原始内容】

这是请求真实调用的用户指令，不能开通套餐或保证平台调用工具。不会伪造“已受理”、隐藏助手文本、修改扣费结果或合成视频任务响应。是否生成仍由平台决定。

## 安装与使用

1. 停用其他旧版扩展，解压 ZIP，加载直接包含 `manifest.json` 的 `dola30` 目录。
2. 必须刷新豆包及 Dola 页面，清除旧页面脚本。诊断顶层版本应为 1.6.34。
3. 国内面板保持“国内生成指令前缀”开启，从网页的视频生成入口选择参数，上传真实素材，手动发送一次剧本。
4. 在“最近一次提交响应”查看是否出现“发出请求含生成指令前缀”。若仍只回文字，不应视为视频已生成。

“生成视频：”是普通文本标签，重复这个标签不能证明工具调用。新前缀不会删除用户贴入的参数稿或重复标签，也不需要用户再手动把新前缀粘贴一次。

只有当前原生消息明确携带视频能力 `ability_type=17` 时才加前缀。普通聊天、历史消息或未知结构不被改成视频请求；面板会提示从视频生成入口发送。已知正文表示和 `input_box_content.user_input_content` 一并处理，保留原生 `reply_message_format`、模型/时长/比例/分辨率及附件。Dola 不安装前缀模块。

## 如何核对前缀是否发出

点击“诊断”，主要看下面两组字段：

| 字段 | 含义 |
| --- | --- |
| `generationIntent.enabled` | 前缀开关状态 |
| `generationIntent.last.added` | 本次签名前处理是否新增前缀；已经存在时不会再加 |
| `generationIntent.last.present` | 处理后的当前视频对象是否含本版完整前缀 |
| `generationIntent.reason` | 添加或跳过的原因，不含原稿 |
| `bridge.lastDraft.intentPrefixAdded` | 原生提交钩子是否补入前缀 |
| `generationEvidence.requestIntent.video` | 发出请求的当前消息是否含已知视频能力 |
| `generationEvidence.requestIntent.present` | 交给 fetch/XHR 的实际请求正文是否含完整前缀 |
| `generationEvidence.requestIntent.inputBoxPresent` | 原生输入框参数中是否观察到前缀；没有该结构时为 false |

签名前的 `last.present=true` 与发出请求的 `requestIntent.present=true` 是两个不同观察点。只有后者为 true，才说明在本插件能解析的实际提交正文中看到了前缀；它仍不能证明服务器受理或扣费。无法读取正文时为 null，不能宣称已检查成功。

`generationEvidence` 保留 URL 改变后的最近一次提交响应；新的提交会更新序号。`verification` 仍为 `UNVERIFIED`。任务/扣费结构字段仅作候选，不从助手“正在生成”“消耗几点”等台词推断任务。实际视频资源见 `mediaParser.qualities`。

## 自动续确认

保留 1.6.28 的默认开启选项“国内自动续确认 · 每轮最多一次”。它等待本轮响应结束，核对新确认回复的模型、时长、比例以及明确给出的分辨率；优先点原生确认按钮，否则通过空的原生编辑框发送一次确认。

旧确认、参数不一致、原生控件不可用、已有草稿、权限/传输错误或用户新操作都会停止。每轮最多一次，不无限回复。没有发送控件时，只撤回自己刚填入且未被改动的固定确认文字。

用户原稿包含“生成参数确认”等标题时，自动续确认仍暂停，避免把刚发送的原稿误认为助手回复；现在 `autoConfirmation.reason` 会明确说明。**这不影响新增的生成指令前缀。** 因此前缀和自动续确认两个开关可分别使用。
